# M4: provenance review worksheet

The human provenance review that #28 asks for, before any release
candidate: every libc16 and libkitchen16 module linked into `PERL.EXE`.
`make release-check` fails until it is recorded (docs/M4-RELEASE.md).
This file lists exactly what is to be reviewed, from the pinned releases
perl16 links today:

| Library | Pinned | Linked modules | Table rows to review | No row yet |
|---|---|---|---|---|
| libc16 | 0.15, sha256 `042b6d2d…0f287` | 103 | 24 of its 38 | `systeme`, `envblock` |
| libkitchen16 | 0.02, sha256 `2ca356b7…2cb85` | 36 | all 5 | none |

The worksheet at the end is generated by `make provenance-worksheet`
(`scripts/check-provenance --worksheet` on `build/rt/perl.map`).
Regenerate it after a library is re-pinned.

## 1. What a review of a row is

A row of a library's `docs/LICENSE-PROVENANCE.md` "Modules" table
covers one or more members. For each row below, the reviewer reads:
- the row and the section it cites ("see …");
- the spec it names, in the library's `docs/spec/`;
- the linked members' source in the library's repository, at the
  release's tag;
- the member's similarity score (`docs/AUDIT.txt`, the large-model
  library's section).

The reviewer then judges whether the record is believable and
complete:
- the code was written from the spec and public sources as stated;
- nothing in it comes from Open Watcom's runtime or another
  incompatible source;
- it can be distributed under MIT with perl16.

A row is approved, or the problem is fixed in the library first.

## 2. How to record it

In the library's repository, not here:
1. Add a **Review** column to the Modules table.
2. In each reviewed row's Review cell, write
   `approved by NAME, YYYY-MM-DD`, followed optionally by a note or a
   commit.
3. Remove "human review pending" from that row's other columns.
   `check-provenance` reads a row that still says it as not reviewed.
4. Release the library and re-pin it in perl16, which needs the new
   SHA-256 in `scripts/fetch-libc16` or `scripts/fetch-libkitchen16`.
   Then `make release-check` reads the new record from the archive
   itself.

A member counts as reviewed only when every row naming it is approved:
its own row, and any row that changes it. For example, row 35's code
reserve changes libc16's `cstart`, and row 31 changes `cstart`,
`exit`, `fopen` and `timecal`.

## 3. Points for the reviewer

These are taken from the records themselves. Each is a question for the
review, not a finding:

- **libc16 row 29** (`rename`, `unlink`, `remove`, `fseek`, `ftell`;
  section "`rename`, `unlink`, `remove`, `fseek` and `ftell`"). An
  earlier version (gr-dos/libc16#11) was written by a session that had
  read parts of GNU `patch` (GPL). The record says these replaced it
  clean-room, in sessions that saw none of #11's code. perl16 links all
  five.
- **libc16 row 33** (the spawn family). `spawnve` and `spawnvpe` score
  0.31 against Open Watcom's large-model library, the highest of any
  member perl16 links that is long enough to judge. The record explains
  it: each is a short wrapper.
- **libkitchen16 row 3** (`fprintf`, `printf`, `vfprintf`). `fprintf`
  scores 0.38 in the large model (16 runs, a call to `vfprintf`, by the
  record).
- **libc16 row 31** (`fromloc`, 0.17). The record says `fromloc` is
  `__libc16_from_local`, moved unchanged out of `timecal`.
- **libc16 row 27** (`intdos`, 0.53). The score is for a member too
  short to judge.
- **Design-session code.** libc16 rows 24–27 and 36–38 (strings, I/O,
  streams, the DOS interface, character classes, time, files) were
  written by the session that wrote their specs. libc16's decision 6
  allows that for ordinary library code, but not for startup, the
  arithmetic helpers, the heap or formatting.
- **Startup** (libc16 rows 1–4). Per the record, a first version,
  written before the spec, was replaced and not consulted.
- **Changes recorded only in prose.** Two are in prose sections and in
  no table row:
  - the 0.14 heap rewrite of `malloc`, `free` and `realloc` ("The
    heap's scaling"), which rows 20–22 don't mention;
  - the compact- and large-model ports ("Memory models (M4)"). perl16
    links the large model.

  Either add them to the rows, or review the sections with the rows.
- **AI authorship.** Both records say that material generated purely by
  an AI may not be protected by copyright. They say the MIT grant
  covers the human contributions, and nothing restricts redistribution
  of the rest. That is relevant to the license review
  (docs/M4-RELEASE.md, section 4).
